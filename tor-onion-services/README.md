# Tor Onion Services

How Tor works, verified at the byte level: the v3 onion-address codec
(base32 of ed25519 pubkey || SHA3-256 checksum || version, per
rend-spec-v3), a CLI that validates any v3 address's checksum offline, plus
plain-language explainers of the 3-hop circuit / 6-hop rendezvous
architecture and an honest threat model of what Tor can and can't hide.
No live Tor needed — this is the offline mechanics portion.

## Dependencies

- **Python 3** (3.10+ recommended)
- **stdlib only** — `hashlib` (SHA3-256), `base64`

## How to run

Entry point is `torguide.py` (argparse):

```bash
python3 torguide.py --help
python3 torguide.py --check-onion duckduckgogg42xjoc72x3sjasowoarfbgcmvfimaftt6twagswzczad.onion
python3 torguide.py --explain        # circuits, onion services, rendezvous
python3 torguide.py --threat-model   # what Tor hides / does NOT hide

# codec self-test (pinned vectors, round-trips, corruption rejection)
python3 onion.py
```

Library use:

```python
from onion import encode_onion, validate_onion

addr = encode_onion(bytes(range(32)))
print(addr)   # aaaqeayeaudaocajbifqydiob4ibceqtcqkrmfyydenbwha5dyp3kead
print(validate_onion(addr + ".onion"))
# (True, 'valid v3 address; ed25519 pubkey=000102...; checksum ... ok')
```

## Key learnings

- **A v3 onion address is self-validating.** The last 2 bytes before the
  version are `SHA3-256(".onion checksum" || pubkey || version)[:2]`, so
  anyone can check an address is well-formed — but only the ed25519 private
  key holder can prove ownership. Validation is offline and instant.
- **DuckDuckGo's real address validates.** The checksum check passing on a
  memorized 56-char string is the strongest possible test of the codec: you
  cannot fake a valid checksum for a wrong address.
- **First-draft test vectors were fiction.** The initial hardcoded vectors
  were invented strings (one wasn't even valid base32). Replaced with
  addresses actually generated by `encode_onion` from fixed keys, then pinned
  — the self-test now checks `pinned == regenerated`, so fabrication can't
  sneak back in.
- **Six hops, zero exits.** Normal browsing: 3-hop circuit ending at an exit
  relay that sees your plaintext. Onion services: your 3 hops + the
  service's 3 hops meet at a rendezvous point — neither side learns the
  other's IP and no exit ever exists. That asymmetry is the whole point of
  onion services, and it's why the threat model differs from exit traffic.
- **The checksum catches typos, not impersonation.** An attacker can
  generate *their own* valid address cheaply; what they can't do is make it
  match someone else's pubkey. Address verification != identity
  verification — same lesson as PGP fingerprints.

## Files

| File | What it does |
|---|---|
| `torguide.py` | **Entry point**: argparse CLI — `--check-onion`, `--explain`, `--threat-model` |
| `onion.py` | v3 codec: `encode_onion` / `decode_onion` / `validate_onion` per rend-spec-v3, pinned test vectors, self-test |

## Limitations

- **Offline mechanics only.** Actually visiting an onion address needs the
  `tor` daemon installed and running with a SOCKS client on 127.0.0.1:9050 —
  documented in `--explain`, not implemented here.
- No ed25519 signing/verification (only the pubkey bytes are handled); the
  checksum covers address *format*, not key ownership proofs.
- v2 (16-char) onion addresses are rejected as invalid — correctly, since
  the v2 network is long dead.
