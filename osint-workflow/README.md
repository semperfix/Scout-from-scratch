# OSINT & Public-Record Investigation

A structured person-investigation workflow with source grading and identity
disambiguation, plus a search-dork battery generator. Everything runs offline:
no live queries, no scraping, no API keys. You run the dorks by hand in your
own search engine; the tool gives you the battery, the rubric for grading
what comes back, and a printable worksheet to keep the investigation honest.

## Dependencies

- **Python 3** (3.10+ recommended)
- **stdlib only** — `argparse`, `textwrap`. No network access, by design.

## How to run

**Generate a dork battery** (entry point `dorkgen.py`):

```bash
python3 dorkgen.py --name "Jordan Ellis" --email j.ellis@example.com \
    --phone "912-555-0147" --username jordanellis92 --location "Savannah, GA"
```

Any subset of inputs works; the battery scales with what you give it
(name-only still yields 19 dorks).

**Methodology pieces:**

```bash
python3 dorkgen.py --rubric       # source-grading rubric (A/B/C/D)
python3 dorkgen.py --checklist    # identity-disambiguation checklist
python3 dorkgen.py --worksheet    # full printable markdown worksheet
python3 dorkgen.py --worksheet --name "Jordan Ellis"   # pre-filled worksheet
```

**Use as a library:**

```python
from dorkgen import build_dorks
for category, dorks in build_dorks(name="Jordan Ellis", location="Savannah, GA"):
    print(category, len(dorks))
```

**Run the validation battery:**

```bash
python3 test_osint.py    # 17 checks: dork counts, categories, worksheet
                         # structure, CLI smoke -- all offline
```

## Key learnings

- **Grading is the workflow, not the dorks.** Anyone can generate search
  strings; the failure mode in person-investigations is treating a C-grade
  aggregator hit as a fact. The rubric's hard rule — a C never promotes to B
  without a second independent source, a D never enters the timeline — is
  what keeps an investigation honest.
- **Disambiguation needs two independent anchors.** Same name is not the same
  person. DOB+address, photo+associates, contact-detail reuse across two
  independent profiles — one anchor is a lead, two is an identity match.
- **Breach data stays manual.** The battery deliberately emits *guidance*
  (check haveibeenpwned by hand) instead of live queries: automated breach
  lookups are both a terms-of-service problem and an opsec problem.
- **The worksheet is the deliverable.** A fill-in-the-blanks markdown file
  (`worksheet-template.md`, also generatable via `--worksheet`) with anchors,
  rubric, checklist, dork checkboxes, a graded-facts timeline, an associates
  graph, and exposure/removal notes — the shape a privacy-exposure audit
  actually takes.

## Files

| File | What it does |
|---|---|
| `dorkgen.py` | **Entry point**: dork battery, `--rubric`, `--checklist`, `--worksheet` |
| `worksheet-template.md` | Printable investigation worksheet (also generated by `--worksheet`) |
| `test_osint.py` | 17-check battery, all deterministic and offline |

## Limitations

- Offline by design: no live search, no scraping, no breach-API queries.
  Dork counts scale with inputs (name-only: 19; full identity set: 32+).
- Search-engine syntax drifts (`site:` scoping, verbatim handling); dorks
  are starting points, not guarantees — verify each against the engine you
  actually use.
- This is a methodology aid, not legal advice: public-record access rules
  vary by jurisdiction, and some pivots (breach data, non-public records)
  have legal and ethical boundaries the worksheet's grading rubric can't
  decide for you.
